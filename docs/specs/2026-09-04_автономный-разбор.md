# Автономный разбор без ноутбука + наблюдаемость каскада (04.09.2026)

Продолжение `2026-08-20_состояние-разбора.md`. Все числа — замеры на живой базе и на реальных
прогонах.

---

## Задача

Владелец закрывает ноутбук и хочет утром открыть сервис с доделанными данными. Значит разбор
очереди должен идти сам: без ручного запуска воркера, без локальных команд добора метрик и
перевода.

## Что было сделано

### 1. Ключи

| Источник | Было | Стало |
|---|---|---|
| Apify | два токена исчерпаны ($5.64 из $5 и $4.49 из $5) | **два новых по $5.00** в `APIFY_API_TOKENS`, плюс рабочий токен продублирован в `APIFY_API_TOKEN` |
| RapidAPI (StarAPI) | два ключа, оба в 429 с 17.08 | **четыре ключа**, лимит сбросился 1 сентября: 95–99 запросов из 100 у каждого |

Ключи вводились через системный диалог `with-secret.sh` и уезжали сразу в `gh secret set` через
stdin — в переписку и в командную строку значения не попадали.

**Потеря:** при первой попытке команда, удалявшая строку `APIFY_API_TOKENS` до записи новой,
стёрла старый второй токен с остатком $0.51. Токен остался только в секрете GitHub (значение
оттуда не читается) и в ротации больше не участвует. Урок записан в разделе «Грабли».

### 2. Работа без ноутбука

* **Расписание вернулось** в `.github/workflows/worker.yml`: `*/15 * * * *`. Пять минут не
  берём — на пустой очереди каждый лишний старт тратит запрос к исчерпанному токену. Минуты
  Actions бесплатны: репозиторий публичный.
* **Импорт с телефона** на https://reelscribe.vercel.app сам дёргает воркер через
  `repository_dispatch` — `GITHUB_DISPATCH_TOKEN` задан в переменных Vercel. Расписание тут
  только страховка.
* **Добор подписчиков** (`backfill_followers`) и **добивка переводов** (`backfill_translate`,
  новый) стали шагами прогона с `if: always()`. Раньше это были ручные команды с ноутбука,
  без которых не считались `er/lpf/cpf`, а иностранные расшифровки оставались без русского
  текста.
* **Датчик квоты** `app/workers/apify_quota.py` (новый) печатается шагами до и после разбора:
  видно, сколько токенов раннер видит и во что обошёлся прогон.

### 3. Наблюдаемость каскада — главное по итогам дня

Днём несколько часов ушло на вопрос «чем скачаны эти рилсы». Ответа не было нигде: каскад
логировал только ошибки, пропуск шага молчал, источник не сохранялся ни в `info`, ни в базе.
Вывод пришлось строить по косвенным признакам — и он оказался **неверным**.

Что теперь:

* каждый источник помечает себя в `info['source']`: `apify-single`, `apify-profile`,
  `instaloader`, `starapi`, `yt-dlp`; воркер пишет это на каждый рилс;
* пропуск шага каскада логируется с причиной один раз за процесс; случай «`APIFY_SINGLE_PRIMARY`
  включён, а токенов нет» — уровнем ERROR, это дыра в конфигурации, а не штатный пропуск;
* в конце drain-прогона печатается сводка: `Итог прогона: apify-single 120, starapi 19, без
  аудио 8, ошибок 2`;
* заведён `docs/диагностика.md` — готовые команды на вопросы «что с очередью», «чем качает»,
  «сколько денег осталось», «кто на cooldown».

### 4. Документация догнала код

`CLAUDE.md` и §4 ТЗ называли первым источником профильный Apify-актор, хотя с 19.08.2026 первым
идёт **одиночный** (`APIFY_SINGLE_PRIMARY`), а профильный при этом флаге пропускается целиком.
Расхождение исправлено, добавлены цены за вызов и указание, какой источник что отдаёт.

### 5. Мелкая починка ротации StarAPI

`_request` в `starapi_downloader.py` обрабатывал только 429. Ключ, аккаунт которого не подписан
на StarAPI, отвечает 403 — такой ответ уходил наверх и ронял весь источник, хотя следующий ключ
в списке рабочий. Теперь 403 трактуется как 429: ключ остывает, берётся следующий. Нашлось на
живом ключе при расширении ротации до четырёх.

## Грабли (чтобы не повторять)

1. **«Есть подписчики — значит качал не Apify» — неверно.** Одиночный актор их не отдаёт
   (`ownerFollowersCount` всегда `null`), но profile-актор дописывает их в том же пайплайне.
   Именно этот признак увёл разбор в неверную сторону.
2. **`/users/me/limits` отстаёт.** Показывал $0.00 при уже потраченных $0.0027. Актуальная
   цифра — `/v2/users/me/usage/monthly`, поле `totalUsageCreditsUsdAfterVolumeDiscount`.
3. **Лог идущего прогона недоступен.** `gh run view --log` и API `/actions/jobs/<id>/logs`
   отдают пусто/404, пока прогон не завершён. Всё, что нужно видеть в реальном времени, должно
   писаться в базу, а не только в лог. Логи Actions живут 90 дней.
4. **Команда, которая удаляет перед записью, теряет данные.** Правку секрета в `.env` делать
   только через скрипт, который сначала проверяет непустоту ввода и делает копию файла, и лишь
   потом заменяет строку — атомарно, через временный файл.
5. **Отсутствие записи в `key_cooldown` — сильный сигнал:** этим токеном за прогон не
   пользовались вообще.
6. **Диагностический шаг обязан иметь `continue-on-error: true`.** Первый прогон с новым шагом
   «Остаток квоты Apify» упал целиком: `Settings` требует `SUPABASE_URL`/`SUPABASE_ANON_KEY`, а
   в env шага передали только Apify-токены. Без `continue-on-error` провалился весь job, и
   воркер не стартовал — датчик сломал ровно то, что должен был наблюдать. Любой новый шаг,
   который только смотрит и печатает, добавляется сразу с этим флагом.
7. **Settings падает на импорте, если не передать обязательные переменные.** Любой скрипт
   `app.workers.*` тянет `app.core.config`, поэтому даже шагу, которому Supabase не нужен,
   переменные Supabase передавать обязательно.
