# Диагностика прода за две минуты

Документ появился 04.09.2026 после разбора, который занял часы вместо минут: прогон воркера
выглядел здоровым, но было непонятно, каким источником он качает рилсы и куда уходят деньги.
Ответа не было ни в логе, ни в базе, и источник пришлось вычислять косвенно — неверно.
Здесь собрано всё, что отвечает на вопрос «что сейчас происходит» напрямую.

Все команды выполняются из `backend/` с локальным venv (`.venv/bin/python`).

---

## Быстрый ответ: одна команда

Разделы 1–7 ниже — способ посмотреть что-то точечно руками. Для общей картины «всё ли в
порядке прямо сейчас» есть единый датчик `scripts/health.py` — он выполняет те же проверки
одним прогоном и печатает сводку по-русски. Запускается **из корня проекта** (не из `backend/`):

```bash
backend/.venv/bin/python scripts/health.py             # без проверки ключей StarAPI
backend/.venv/bin/python scripts/health.py --starapi    # + живая проверка каждого ключа StarAPI
```

Показывает по разделам: очередь (`jobs`/`transcripts` по состояниям), дыры в данных (рилсы,
не видные воркеру из-за отсутствия записи в `jobs`; без подписчиков/просмотров; готовые
иностранные расшифровки без перевода), деньги Apify по каждому токену ротации, ключи StarAPI
(только с флагом `--starapi` — иначе тратит их квоту), активные записи `key_cooldown`, последние
прогоны воркера (`gh run list` + таблица `worker_runs`, если миграция 0004 уже применена) и
короткий вердикт в 3-5 строк.

Падение одной секции (нет сети, нет `gh`, таблица ещё не создана) не роняет отчёт — она просто
помечается недоступной. Результат сохраняется в `.health/health-<дата>-<время>.json`
(гитигнорится) до печати сводки — путь к файлу выводится последней строкой, дальше его можно
пересмотреть без повторного дорогого прогона.

## 1. Что с очередью

```bash
.venv/bin/python -c "
from collections import Counter
from app.core.db import get_db
db = get_db()
rows, start = [], 0
while True:
    r = db.table('transcripts').select('status').range(start, start + 999).execute().data
    rows += r
    if len(r) < 1000: break
    start += 1000
print(Counter(x['status'] for x in rows))
"
```

`queued` — ждут разбора, `done` — готовы, `no_audio` — фото/карусели (терминально, ретраить
бессмысленно), `failed` — ошибки с причиной в `fail_reason`.

**Ловушка:** рилс со статусом `queued` может не иметь записи в `jobs` — воркер берёт работу
именно из `jobs` и такие рилсы не видит. Проверять надо стыком двух таблиц, а не одной.

## 2. Чем скачиваются рилсы

Каждый источник помечает себя в `info['source']`: `apify-single`, `apify-profile`,
`instaloader`, `starapi`, `yt-dlp`. Воркер пишет источник в лог на каждый рилс и печатает
сводку в конце прогона (`backend/app/workers/run.py`).

**Ловушка, стоившая часа 04.09:** «у рилса заполнены подписчики — значит качал не Apify» —
**неверно**. Одиночный актор подписчиков не отдаёт, но profile-актор дописывает их в том же
пайплайне, и в базе они появляются одинаково при любом источнике.

## 3. Деньги Apify

```bash
.venv/bin/python -m app.workers.apify_quota
```

Печатает по каждому токену ротации две цифры: свежую (`/v2/users/me/usage/monthly`) и
отстающую (`/users/me/limits`). **Смотреть надо свежую.** `/limits` агрегируется с задержкой в
несколько минут и показывает $0.00 при уже потраченных деньгах — именно на этом строился
неверный вывод 04.09.

Тот же датчик запускается шагами прогона на Actions — до и после разбора, разница и есть цена.

Ориентир цены: **$0.0027** за рилс одиночным актором + **$0.0026** за автора profile-актором
(с учётом попаданий в общий `followers_cache` — около $0.0075 на рилс суммарно).
Бесплатный кредит — $5 на аккаунт за цикл; цикл у каждого аккаунта свой, дата видна в выводе.

## 4. Ключи StarAPI

Бесплатный тариф — 100 запросов в месяц на ключ, сброс 1 числа. Живость и остаток:

```bash
.venv/bin/python -c "
import httpx
from app.core.config import settings
for i, k in enumerate(settings.rapidapi_key_list, 1):
    r = httpx.post('https://%s/instagram/media/get_info_by_shortcode' % settings.starapi_host,
                   headers={'x-rapidapi-key': k, 'x-rapidapi-host': settings.starapi_host,
                            'Content-Type': 'application/json'},
                   json={'shortcode': 'DRnVrkNAMtn'}, timeout=45)
    print('ключ #%d …%s: HTTP %s — остаток %s из %s' % (
        i, k[-6:], r.status_code,
        r.headers.get('x-ratelimit-requests-remaining', '?'),
        r.headers.get('x-ratelimit-requests-limit', '?')))
"
```

Каждая такая проверка тратит по одному запросу из сотни на каждый ключ.

- **HTTP 429** — месячная сотня выбрана.
- **HTTP 403 «You are not subscribed to this API»** — ключ живой, но его аккаунт не подписан на
  StarAPI: подписка оформляется в кабинете RapidAPI, тариф Basic бесплатный.
- Ключи опознаются по последним шести символам — так же, как их печатает лог воркера.

## 5. Кто на cooldown

```bash
.venv/bin/python -c "
from app.core.db import get_db
for r in get_db().table('key_cooldown').select('*').order('until', desc=True).limit(10).execute().data:
    print(r)
"
```

Таблица общая для всех воркеров: ключ, получивший 429/403, остывает и не тратит попытки у
соседних процессов. `key_ref` — хэш ключа, самих значений в базе нет.

**Отсутствие записи о токене — сильный сигнал:** значит этим токеном за прогон вообще не
пользовались.

## 6. История прогонов (`worker_runs`)

Заведено 04.09.2026 миграцией `supabase/migrations/0004_observability.sql` — до неё ответить на
«что происходит прямо сейчас» и «во что обошёлся прогон» можно было только логами Actions, а они
доступны лишь после завершения прогона (см. §7) и живут 90 дней. Таблица `worker_runs` пишется
воркером в drain-режиме (`app/workers/run.py` через `app/workers/run_log.py`): одна строка на
прогон, создаётся в начале и обновляется по ходу.

```bash
.venv/bin/python -c "
from app.core.db import get_db
for r in get_db().table('worker_runs').select('*').order('started_at', desc=True).limit(5).execute().data:
    print(r)
"
```

Поля: `finished_at` NULL — прогон ещё идёт; `outcome` — `drained` (очередь разобрана) или
`timeout` (упёрлись в лимит времени Actions, `crashed`/NULL не проставляются кодом сейчас);
`jobs_done`/`jobs_no_audio`/`jobs_failed` — счётчики; `sources` — `{"apify-single": 120, ...}`,
то же самое, что печатает в лог `_log_run_summary`; `apify_spent_usd` — разница расхода Apify
между снимками в начале и в конце прогона (может быть `NULL`, если снять расход не удалось).

Источник конкретной расшифровки — в `transcripts.source` (`apify-single` / `apify-profile` /
`instaloader` / `starapi` / `yt-dlp`):

```bash
.venv/bin/python -c "
from collections import Counter
from app.core.db import get_db
rows = get_db().table('transcripts').select('source').eq('status', 'done').execute().data
print(Counter(r['source'] for r in rows))
"
```

**Best-effort — обе вещи могут молчать.** Если таблицы `worker_runs` ещё нет в базе или колонки
`source` ещё нет в `transcripts` (миграция не применена), воркер продолжает разбирать очередь как
ни в чём не бывало: `run_log.py` выставляет модульный флаг после первой неудачи и просто
перестаёт писать, а `run.py` при неудаче записи `source` тут же повторяет тот же update без
него — расшифровка не теряется. Практическое следствие: **у всех записей до 04.09.2026 `source`
пуст**, и если увидите пустую `worker_runs` при живом проде — это тоже нормально, значит колонка
или таблица ещё не докатились до этой базы.

## 7. Логи прогона на Actions

```bash
gh run list --workflow=worker.yml --repo ilfaaat-sistema/reelscribe --limit 5
gh run view <run-id> --repo ilfaaat-sistema/reelscribe --log > run.log
```

**Важно:** лог доступен только после завершения прогона. У идущего `--log` возвращает пусто, и
API `/actions/jobs/<id>/logs` отвечает 404 — смотреть в веб-интерфейсе или дождаться конца.
Логи живут 90 дней, поэтому всё, что нужно надолго, должно попадать в базу, а не только в лог.

Полезные срезы по сохранённому логу:

```bash
grep -c 'acts/apify~instagram-scraper' run.log        # вызовов одиночного актора
grep -c 'acts/apify~instagram-profile-scraper' run.log # вызовов profile-актора (подписчики)
grep -c 'starapi1.p.rapidapi.com' run.log             # обращений к StarAPI
grep 'Итог прогона' run.log                            # сводка по источникам
```

## 8. Запуск и остановка разбора

```bash
gh workflow run worker.yml --repo ilfaaat-sistema/reelscribe   # запустить
gh run cancel <run-id> --repo ilfaaat-sistema/reelscribe       # остановить
```

Расписание (`schedule` в `.github/workflows/worker.yml`) включается и выключается
комментированием двух строк. Импорт через API дёргает воркер сам — `repository_dispatch`,
токен задан в переменных Vercel.

Задания, брошенные отменённым прогоном, вернёт в очередь `_requeue_stale` — через 45 минут
после того, как их взяли в работу. Терять их не надо бояться.

## 9. Миграции: `db push` здесь не работает, и это нормально

Выяснено 04.09.2026 при попытке применить `0004_observability.sql`.

Проект Supabase `kcfkhebtlyqgbzaajgiv` — **общий для нескольких приложений**: ReelScribe живёт в
схеме `public`, рядом в своих схемах живут `sporta` и `avatar_bot`. В истории миграций базы
лежат 55 версий соседей, которых в нашем каталоге нет и быть не должно. `supabase db push`
требует, чтобы вся история базы была представлена локально, поэтому он останавливается с
«Remote migration versions not found in local migrations directory» — и `--include-all` не
помогает, проверка идёт по remote-стороне.

**Подсказку CLI `supabase migration repair --status reverted <55 версий>` не выполнять
никогда.** Она пометит чужие миграции отменёнными, и следующий push соседнего приложения
накатит их SQL повторно — сломается не наш проект, а чужие.

Что работает:

* `supabase link --project-ref kcfkhebtlyqgbzaajgiv --password ""` — линковка проходит **без
  пароля**, после неё работают `migration list --linked` и `migration repair`.
* `supabase migration repair --status applied <версия>` — безопасная форма: SQL не выполняется,
  просто фиксируется, что версия уже применена. Так 04.09.2026 были отмечены `0001`–`0003`.
* Сам SQL применяется **напрямую**, а не через push: нужен пароль Postgres (Settings → Database,
  там же кнопка сброса — ключи API при сбросе не меняются). Драйвер `psycopg` в venv бэкенда
  уже стоит. После применения версия помечается `repair --status applied`.

Пароль в чат не вставлять — вводить через системный диалог `~/.claude/scripts/with-secret.sh`.

## 10. Чего эти команды НЕ говорят

- Правильно ли распознана речь — только глазами по конкретному рилсу.
- Почему источник промахнулся по конкретному рилсу — смотреть строку ошибки в логе рядом с
  его shortcode.
- Сколько на самом деле осталось денег у аккаунта Apify, если токен от этого аккаунта потерян:
  в ротации его нет, и датчик его не видит — заводить заново из кабинета Apify.
