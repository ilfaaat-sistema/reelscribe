## Задача A. Общий cooldown API-ключей между воркерами

### Проблема

Cooldown ключей после HTTP 429 живёт **в памяти процесса**: `_cooldown` в
`backend/app/pipeline/starapi_downloader.py`, `_cooldown` и `_actor_cooldown` в
`backend/app/pipeline/apify_client.py`.

Пока воркер был один, это работало. Теперь их может быть два одновременно — на GitHub Actions и
локальный на Mac. Двойной обработки задания не будет (claim атомарный, `backend/app/workers/run.py`),
но каждый процесс видит свою картину квот: оба независимо упираются в 429 по одному ключу и
продлевают простой вместо того, чтобы переждать его один раз. Сейчас это закрыто только
предупреждением в `README.md`, которое легко нарушить случайно.

### Что сделать

- Миграция `supabase/migrations/0003_key_cooldown.sql`: таблица вида
  `key_cooldown(provider text, key_ref text, actor text null, until timestamptz, primary key (provider, key_ref, actor))`.
- **Секреты в базу не писать.** `key_ref` — идентификатор, а не ключ: sha256 (первые 16 символов)
  либо последние 6 знаков, как уже делают логи (`token[-6:]` в `apify_client.py`).
- Недоступность базы не должна ронять скачивание: при ошибке — фолбэк на нынешнее поведение в
  памяти (best-effort, образец — `_check_rate_limit` в `backend/app/api/import_.py`).
- Разделение «cooldown аккаунта» и «cooldown пары (токен, actor)» из `apify_client.py` **сохранить**:
  402 и `platform-feature-disabled` относятся к конкретному актору, глобальный бан токена убивал бы
  основной каскад загрузки.
- После этого снять предупреждение из `README.md` и `CLAUDE.md`.

### Проверка

Запустить локальный воркер и `workflow_dispatch` одновременно на непустой очереди: после 429 у
одного второй не должен долбить тот же ключ (видно в логах обоих).

**Делать до большого прогона задачи B** — именно там два воркера подерутся за ключи гарантированно.

### ~~Открытый вопрос~~: что значит «проанализировать» — ЗАКРЫТО 2026-08-10

Ответ пользователя: **отдельный анализ не нужен.** Цель задачи B — чтобы все 923 рилса были
расшифрованы и лежали в базе; разбирать их пользователь будет сам уже существующими экранами
сервиса («у меня в сервисе были уже все необходимые экраны»).

Из этого следует: новый функционал (обобщение тем по расшифровкам, отдельный экран аналитики,
сравнение двух наборов) в рамках этой задачи **не делается**. Задача B сводится к прогону
пайплайна по всем ссылкам и укладыванию в квоты.

### Что показал реальный прогон 2026-08-10 (замеры, не оценки)

Прогнали пробную партию 25 + партии 01–03 по 120. Итог: **~$10,9 (870 ₽) за ~170 рилсов**, обе
квоты Apify исчерпаны, оба ключа RapidAPI исчерпаны (лимит 100 запросов/мес на ключ, сброс ~28.08).

**Параллельность вчетверо дороже, а не на 10–15%.** На одном воркере цена была $0,0188 за рилс,
после включения matrix из 4 шардов — $0,053…$0,075. Причина: `_followers_cache` в
`apify_client.py` живёт в памяти процесса, поэтому каждый воркер скрейпит профиль одного и того же
автора заново. В этой выборке авторы почти не повторяются (185 авторов на 234 рилса), так что
профильный скрейп идёт почти на каждый рилс и множится на число воркеров. Воркер откачен на
`shard: [1]`; возвращать параллельность можно **только** после переноса кэша в общую базу.

**Деградация каскада видна по данным, а не по логам.** Пока StarAPI отвечал, метрики были у 100%
расшифрованных (51/51 и 57/57). После исчерпания RapidAPI остался только yt-dlp — и доля рилсов
без подписчиков сразу выросла до 25% (3 из 12 в партии 02). Проверять качество прогона нужно
именно так: считать долю `author_followers is null` среди `filter=done`, а не смотреть на счётчик
готовых.

### ~~Задача C~~. Отдельная операция «дотянуть метрики» — ИНСТРУМЕНТ УЖЕ ЕСТЬ

Идея пользователя, 2026-08-10: метрики тянутся только вместе с расшифровкой, поэтому рилс,
обработанный без квоты, остаётся с текстом, но без `author_followers`, и чинится только полным
перезапуском — то есть повторной оплатой скачивания и распознавания.

**Писать ничего не нужно: `backend/app/workers/backfill_followers.py` делает ровно это.** Берёт
рилсы с пустым `author_followers`, группирует по авторам (один вызов на автора, не на рилс) и
проставляет подписчиков через `resolve_followers`. `er`/`lpf`/`cpf` — generated-колонки Postgres,
пересчитываются сами.

```
python -m app.workers.backfill_followers                  # все
python -m app.workers.backfill_followers --session <UUID> # одна сессия
```

Проверено на данных 10.08: из 386 расшифрованных без подписчиков осталось 5 рилсов, и у всех
пятерых `author_handle` заполнен — то есть скрипт покрывает их полностью (3 уникальных автора,
3 вызова профиля). Запустить после восстановления квот: Apify — 14.08 и 07.09.

**Единственный непокрытый случай** — рилс, у которого пуст и `author_handle`: скрипт его
отфильтрует (`.not_.is_('author_handle', 'null')`), а дотянуть автора можно только запросом по
shortcode (StarAPI `/instagram/media/get_info_by_shortcode`). Сейчас таких рилсов **0**, поэтому
код под этот случай не пишем — понадобится, когда появится хоть один.

### Задача D. Кэш подписчиков в общую базу

Та же болезнь, что и у задачи A (cooldown), и тот же рецепт: `_followers_cache` вынести из памяти
процесса в таблицу Supabase, best-effort с фолбэком на память. Без этого параллельные воркеры
множат самый дорогой вызов каскада. Делать вместе с задачей A — они правятся в одном файле.

### Улучшение на будущее (не блокер)

`frontend/src/pages/Import.jsx` читает файл через `FileReader` и отправляет его содержимое целиком
в поле `links_text` (строка 122). Для файлов больше 4,5 МБ это вернёт 413 на Vercel. Стоит вытаскивать
ссылки регуляркой прямо в браузере и слать только их — тело запроса уменьшится примерно в сто раз.
Сейчас не мешает (39,7 КБ), но помешает на следующей большой выгрузке.
