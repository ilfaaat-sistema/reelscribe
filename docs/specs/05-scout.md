# ТЗ 05. Разведка по нику автора через официальный Graph API

**Статус:** ТЗ

## Проблема / цель

Сервис узнаёт метрики рилса только **побочным продуктом скачивания**: чтобы понять, залетел ролик
или нет, его надо сначала скачать платным каскадом (Apify ~$0.0027 за рилс), а подписчиков автора
добрать отдельным вызовом профильного актора ($0.041 за автора). Значит, чтобы найти десять
залетевших роликов из сотни, мы платим за сотню скачиваний.

11.09.2026 к проекту подключён официальный Instagram Graph API (Business Discovery) — он отдаёт те
же цифры **бесплатно и до скачивания**. Цель: новый вход в сервис «по нику автора», где видно всю
его ленту с просмотрами и залётностью без единого скачивания, и откуда на расшифровку уходят
только выбранные ролики.

Побочно закрывается вторая дыра: подписчики автора перестают стоить денег.

### Что проверено на живом API (замеры 11.09.2026, не документация)

Доступ: приложение `ReelScribe` (App ID `1062609923026979`), системный пользователь
`reelscribe-worker`, бессрочный маркер в `backend/.env` как `META_IG_TOKEN`, точка входа —
`META_IG_USER_ID=17841407230723543` (аккаунт `@ilfaaat_sistema`). Рабочий образец запроса и разбора
ответа — `scripts/probe_business_discovery.py`, сырые ответы кладёт в `.probe/`.

Запрос: `GET https://graph.facebook.com/v23.0/{META_IG_USER_ID}`, параметр
`fields=business_discovery.username(НИК){ПОЛЯ_ПРОФИЛЯ,media.limit(N){ПОЛЯ_МЕДИА}}`.

| Что | Результат замера |
|---|---|
| Поля профиля | `followers_count`, `media_count`, `username`, `name`, `biography`, `website`, `profile_picture_url`, `follows_count` — все приходят |
| Поля медиа | `id`, `caption`, `like_count`, `comments_count`, `view_count`, `media_type`, `media_product_type`, `media_url`, `thumbnail_url`, `permalink`, `timestamp` |
| Размер страницы | `media.limit(100)` работает; пагинация `media.limit(N).after(<курсор>)` проверена — вторая страница приходит |
| Часовой бюджет | ~250–300 вызовов (23 запроса щупа = 8% по заголовку `x-app-usage`) |

**Ограничения, которые определяют архитектуру — проверены, не предполагаются:**

1. **`media_url` у рилсов пустой** — 0 из 9, тогда как у обычных постов 10 из 10. Прямой запрос
   `/{media-id}?fields=media_url` по чужому рилсу возвращает ошибку 100. Значит **скачивание аудио
   остаётся на существующем каскаде** (Apify → instaloader → StarAPI → yt-dlp), Graph API его не
   заменяет ни при каких условиях.
2. **`shortcode` не поддерживается** — Meta отдаёт ошибку «unsupported fields». Берётся из
   `permalink` (последний сегмент пути). Критично: `reels.shortcode` — ключ дедупликации всей базы.
3. **`view_count` только у рилсов** (9 из 9), у FEED-постов его нет вообще.
4. **По ссылке на рилс автора не узнать**: `oEmbed` требует App Review, получен отказ `(#10)`.
   Поэтому вход нового сценария — **ник**, и старый импорт по ссылкам не меняется.
5. Работает только по публичным Business/Creator аккаунтам.

## Пользовательский сценарий

1. Владелец открывает `/scout`, вводит ник конкурента, жмёт «Разведать».
2. Видит карточку автора (аватар, имя, подписчики, био) и таблицу его публикаций: просмотры,
   лайки, комментарии, залётность — с той же раскраской, что в основной таблице результатов.
   У роликов, которые уже есть в базе, стоит пометка «расшифрован».
3. Сортирует по просмотрам или залётности, отмечает галочками интересные ролики.
4. Жмёт «Расшифровать выбранные (N)» — попадает на привычный экран прогресса, дальше всё как при
   обычном импорте.
5. Позже, когда захочет узнать свежие цифры по уже разобранному автору, жмёт иконку «↻» — метрики
   обновляются бесплатно, без перекачивания.

## Функциональные требования

1. Разведка по нику: профиль + до 100 публикаций за вызов, подгрузка следующих страниц курсором.
2. Найденное сохраняется в базу; повторная разведка того же автора не плодит дублей и добавляет
   новый замер в историю (для будущей динамики просмотров).
3. В выдаче у каждого ролика видно, есть ли он уже в базе и в каком статусе расшифровки.
4. Отправка выбранных роликов в существующую очередь скачивания и расшифровки.
5. Освежение метрик уже разобранных роликов автора по кнопке.
6. Подписчики автора берутся сначала из Graph API (бесплатно), Apify остаётся запасным.
7. Аккаунт, которого нет или который не Business/Creator, даёт понятное человеку сообщение, а не
   техническую ошибку.

## Утверждённые решения

**1. Разведка живёт в своих таблицах, а не сыплет в `reels`.** Соблазн писать находки прямо в
`reels` с апсертом по `shortcode` велик — тогда освежение метрик получается само собой. Но в базе
сейчас 2624 рилса, а `/results` без сессии показывает **всё**: разведка десяти авторов добавит туда
тысячу строк без расшифровок, и экран результатов, аналитика и экспорт наполнятся тем, чего
владелец туда не клал. Это регресс работающего сценария. Поэтому находки живут в `scout_*`, а в
`reels` ролик попадает **только** когда его отправили на расшифровку — обычным импортом.

**2. Подписчики через Graph API — с быстрым откатом на Apify.** У Apify лимитов практически нет, у
Graph API жёсткий часовой потолок. Импорт сотни роликов от разных авторов способен съесть весь
бюджет и обвалить заодно разведку. Поэтому при первом же признаке лимита ставится cooldown на
остаток часа через существующий `shared_state`, и последующие вызовы идут сразу в Apify, не трогая
сеть.

**3. Освежение метрик — по автору, а не по ролику.** Один вызов возвращает до 100 публикаций
автора, поэтому обновить разом все его ролики дешевле, чем каждый поштучно.

**4. Номер миграции — 0006, а не 0005.** В `main` лежит `0004_observability.sql`, а в ветке
`module/collections` — `0004_collections.sql`: два разных файла под одним номером. Миграция
collections в боевую базу ещё не применена (колонок `collection`, `source_kind`, `source_name`,
`added_at` в `reels` нет) — чинится переименованием её файла, но чинить должна сессия того модуля.
Мы берём 0006 и не зависим от того, когда это произойдёт.

## Вне рамок

Автомониторинг списка авторов по расписанию (вторая итерация), графики динамики просмотров,
поиск по хэштегам (нужен отдельный App Review), собственная статистика аккаунта владельца
(охваты, сохранения — требует входа в Instagram), скачивание медиа через Graph API (невозможно,
см. ограничение 1).

## Реализация (готовый план исполнения — сессия модуля НЕ планирует заново)

- **Модель сессии:** `sonnet`. Модуль объёмный, но спроектирован: контракты и схема БД заданы ниже.

### Этап 1. Фундамент — последовательно, до всего остального

Файлы: `backend/app/pipeline/business_discovery.py`, `backend/app/core/config.py`,
`backend/tests/test_business_discovery.py`, `supabase/migrations/0006_scout.sql`.

**Клиент `business_discovery.py`:**

- `async def fetch_author(username, media_limit, after=None) -> AuthorSnapshot` — один вызов,
  возвращает профиль, список медиа и курсор следующей страницы. `media_limit=1` — режим «нужны
  только подписчики» (для `followers.py`).
- `async def fetch_author_all(username, max_pages=3) -> AuthorSnapshot` — пагинация курсором.
- `def shortcode_from_permalink(permalink) -> str | None` и
  `def media_to_reel_type(product_type) -> str` (`REELS` → `reel`, иначе `post`) — **перенести** из
  `scripts/probe_business_discovery.py` и переключить щуп на импорт отсюда, чтобы формула жила в
  одном месте.
- **Исключения различать обязательно:** `AuthorNotFound` (аккаунта нет или он личный — нормальный
  исход, cooldown НЕ ставить) и `RateLimited` (временно, cooldown ставить). Перепутать их значит
  либо забанить маркер из-за опечатки в нике, либо сказать «Instagram не работает» про личный
  аккаунт.
- **Лимиты:** читать заголовок ответа `x-app-usage` (JSON с `call_count` 0–100); при
  `call_count > settings.meta_ig_usage_soft_limit` проактивно ставить cooldown до конца часа через
  `backend/app/pipeline/shared_state.py` (`save_cooldown`/`load_cooldowns`, провайдер `'meta_ig'`).
  Механизм межпроцессный и уже работает для Apify и RapidAPI — свой не изобретать.
- Маркер **не логировать никогда** — ни в отладке, ни в отчётах, ни в тестах.

**Настройки в `config.py`** (аддитивно, новыми полями класса `Settings`): `meta_ig_token: str = ''`,
`meta_ig_user_id: str = ''`, `meta_ig_api_version: str = 'v23.0'`,
`meta_ig_usage_soft_limit: int = 90`, `scout_media_page_size: int = 50`.

**Миграция `0006_scout.sql`** — DDL **показать владельцу и дождаться подтверждения** перед
применением (правило проекта):

| Таблица | Поля |
|---|---|
| `scout_authors` | `username text PK`, `name`, `followers int`, `follows int`, `media_count int`, `biography`, `website`, `avatar_url`, `checked_at timestamptz`, `last_error text` |
| `scout_media` | `media_id text PK`, `username text → scout_authors`, `shortcode text`, `permalink`, `caption`, `media_type`, `product_type`, `views int`, `likes int`, `comments int`, `posted_at timestamptz`, `first_seen_at`, `last_seen_at` |
| `scout_metrics` | `id uuid PK`, `media_id text`, `views int`, `likes int`, `comments int`, `measured_at timestamptz`, `source text` (`scout` \| `refresh`) |

Индексы: `scout_media (username, views desc)`, `scout_media (shortcode)`,
`scout_metrics (media_id, measured_at desc)`. RLS — как у остальных таблиц:
`anon_full_access_*`, `for all to anon, authenticated using (true) with check (true)`.

**Контракт ответа, которым дальше пользуются этапы 2 и 3** (зафиксировать на этом этапе, дальше не
менять): `ScoutResponse { author: ScoutAuthor, items: ScoutMedia[], next_after: str|null }`, где
`ScoutMedia` содержит `media_id, shortcode, permalink, caption, type, views, likes, comments,
posted_at, er, in_base, transcript_status`.

### Этап 2. Три параллельных куска — файлы не пересекаются

**2а. Бэкенд-разведка** (субагент, `sonnet`). Файлы: `backend/app/api/scout.py`,
`backend/app/services/scout_service.py`, `backend/app/models/schemas.py` (только новый блок
`# ── Scout ──` в конце), `backend/app/main.py` (одна строка `include_router`),
`backend/tests/test_scout_api.py`.

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/api/scout/{username}` | разведка: профиль + медиа, с пометкой «уже в базе» |
| `GET` | `/api/scout/recent` | недавно разведанные авторы из `scout_authors` |
| `POST` | `/api/scout/transcribe` | отправить выбранные в очередь |
| `POST` | `/api/scout/{username}/refresh-metrics` | освежить метрики разобранных роликов автора |

- Апсерты **обязательно с явным `on_conflict`** (`upsert(rows, on_conflict='media_id')`), иначе
  PostgREST матчит конфликт по первичному ключу и либо плодит дубли, либо падает на уникальном
  индексе.
- `POST /api/scout/transcribe` **не изобретает импорт**: собирает `permalink` выбранных и зовёт
  существующий `handle_import` из `backend/app/services/import_service.py` с **`pull_stats=False`**
  — иначе каскад скачивания перетрёт свежие метрики Graph API своими, более скудными. Ответ —
  `session_id`, фронт уходит на `/processing/<id>`.
- `in_base` и `transcript_status` — джойном по `shortcode` к `reels` и `transcripts`. Помнить про
  лимиты PostgREST: `.select()` без `.range()` режется на ~1000 строк, `.in_()` бьётся чанками по
  200 — образцы в `backend/app/api/errors.py` (`_fetch_all_jobs`, `_fetch_in_chunks`).
- `AuthorNotFound` → HTTP 404 с русским текстом «аккаунт личный или не найден, Instagram не отдаёт
  по нему статистику»; `RateLimited` → HTTP 429 с указанием, через сколько повторить.
- Бизнес-логика — в `scout_service.py`, в роутере только валидация и вызов (конвенция проекта).

**2б. Подписчики** (субагент, `sonnet` — не haiku, риск регрессии платного каскада). Файлы:
`backend/app/pipeline/followers.py`, `backend/tests/test_followers.py`.

- Порядок источников: Graph API → Apify → instaloader. Сигнатура `resolve_followers` **не
  меняется**, поэтому `workers/run.py:78` и `workers/backfill_followers.py:51` не трогаем.
- Общий кэш `followers_cache` через `shared_state` читается ДО любого сетевого вызова и пишется
  после — кэш общий на автора, а не на источник.
- Перед правкой прогнать `grep -rn "get_followers_via_apify"` и убедиться, что её не зовут в обход
  `resolve_followers`.
- **При пустом `META_IG_TOKEN` поведение обязано остаться ровно сегодняшним** — это и есть главная
  проверка на регрессию.

**2в. Фронтенд** (субагент, `sonnet`). Файлы: `frontend/src/pages/Scout.jsx`,
`frontend/src/api/scout.js`, `frontend/src/App.jsx`, хвост `frontend/src/index.css`,

- **`frontend/src/api/client.js` не трогать вообще** — свои вызовы в отдельном `api/scout.js`.

- Блок стилей `/* SCOUT */` — **в самый конец** `index.css`.
- Оформление копировать из `frontend/src/pages/Results.jsx` (массив `COLS`, классы `.er`, `.tag`,

## Критерии приёмки

1. `cd backend && pytest && ruff check .` — зелёные; `cd frontend && npm run build` — без ошибок.
2. `GET /api/scout/maximzheleznov` → 870 подписчиков, 19 медиа, из них 9 рилсов с непустыми
   `views`; у `DcL_0CDs0hn` просмотров ≈32 тыс.; `shortcode` корректно вынут из `permalink`.
3. Крупный аккаунт (`nasa`) — приходит больше одной страницы, пагинация курсором работает.
4. Личный или закрытый аккаунт → HTTP 404 с понятным русским текстом, **cooldown не ставится**:
   следующий запрос к нормальному нику проходит сразу.
5. Повторная разведка того же автора: вторых строк в `scout_media` не появилось, в `scout_metrics`
   добавилось ровно по одной строке на медиа.
6. Имитация превышения `x-app-usage` → следующий вызов получает 429 без похода в сеть, и cooldown
   виден другому процессу через таблицу `key_cooldown`.
7. Выбор двух роликов → «Расшифровать выбранные» → создана одна `import_sessions` и два `jobs`;
   `/processing/<id>` показывает прогресс; ролики доходят до расшифровки обычным каскадом; метрики,
   выставленные разведкой, после прогона воркера **не перетёрты**.
8. Кнопка освежения по автору обновляет `views/likes/comments` у его роликов и пишет строки в
   `scout_metrics`.
9. **Регрессия:** при пустом `META_IG_TOKEN` `resolve_followers` ведёт себя ровно как сегодня
   (Apify → instaloader), ни одна ветка не падает на пустых настройках; экраны `/results`,
   `/history`, `/errors` и обычный импорт по ссылкам не изменились; в `/results` не появилось ни
   одного ролика из разведки.
