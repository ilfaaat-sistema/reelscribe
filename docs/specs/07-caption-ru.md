# ТЗ 07. Перевод текста поста на русский

**Статус:** в работе (заведено 23.09.2026)
**Ветка:** `module/caption-ru`, worktree `worktrees/caption-ru`

## 1. Зачем

Расшифровка речи переводится с самого начала — у неё в карточке есть переключатель
«Оригинал / Русский». А **текст поста** (`caption`) показывается только в оригинале, хотя
заметная часть сохранённого — иностранные авторы. Владелец читает ленту темами и на англоязычных
подписях спотыкается.

Замер 23.09.2026: подписей в базе **2687**, из них примерно четверть не на русском —
около 700 записей, ~300 тыс. символов.

**Денег это не стоит:** `DEEPL_API_KEY` не задан, `translate_to_ru` работает через бесплатный
Google-переводчик. Расход — только время воркера и пауза между записями, чтобы бесплатный сервис
не срезал по частоте (в `backfill_translate.py` это `_PAUSE_SEC = 0.7`).

## 2. Модель данных

Миграция `supabase/migrations/0006_caption_ru.sql`:

```sql
alter table public.reels add column if not exists caption_ru text;
```

Поле живёт рядом с `caption`, в `reels`: подпись принадлежит посту, а не расшифровке.
Отдельной таблицы не нужно, связь один-к-одному.

## 3. Когда переводим

Язык подписи не равен языку речи: `transcripts.language` определяется по аудио и к `caption`
отношения не имеет. Поэтому решение принимается по самому тексту — доля кириллических букв
среди буквенных символов ниже 30% при не менее чем 12 буквах. Порог и правило вынести в одну
функцию, чтобы пайплайн и бэкфилл судили одинаково.

Пустой `caption`, подпись из одних хэштегов и эмодзи (букв меньше порога) — не переводим,
`caption_ru` остаётся `null`.

## 4. Контракт

| Что | Имя |
|---|---|
| Колонка БД | `public.reels.caption_ru` |
| Поле в JSON рилса | `caption_ru: string \| null` |
| Колонка экспорта | `caption_ru` → «Текст поста (рус.)» |
| Поиск `q` в `/api/reels` | ищет также по `caption_ru` |
| Общий тумблер фронта | существующий «Перевод на русский» (`showTr`) распространяется на текст поста |

Правило показа везде одинаковое: при включённом переводе показываем `caption_ru`, а если он
пуст — оригинал `caption`, без пустых мест и без пометок об ошибке.

## 5. Работы

### A. Бэкенд

- `backend/app/workers/run.py`: после расшифровки, рядом с переводом текста, переводить и подпись
  по правилу из §3; писать `reels.caption_ru`. Перевод подписи не должен ронять обработку рилса:
  ошибка переводчика логируется, рилс остаётся успешным.
- Новый `backend/app/workers/backfill_caption.py` — строго по образцу `backfill_translate.py`
  (argparse, `_PROGRESS_EVERY`, `_PAUSE_SEC`, `--session`, идемпотентность: берём только записи
  с непустым `caption` и пустым `caption_ru`). Обязателен `--dry-run`: сколько подписей подпадает
  под правило, без единого запроса к переводчику.
- `schemas.py`: `caption_ru: Optional[str]` в `ReelRow`/`ReelDetail`.
- `reels.py`: отдавать поле; в поиске `q` добавить `caption_ru` к уже искомым `caption` и тексту
  расшифровки — **не сломав текущее поведение поиска**.
- `export_.py`: колонка и русский заголовок.

### B. Фронтенд

- `ReelDrawer.jsx`: у блока «Текст поста» переключатель «Оригинал / Русский» — ровно такой же,
  как у расшифровки ниже, теми же классами. Если `caption_ru` пуст, переключатель не показываем.
- `Results.jsx`: колонка «Текст поста» учитывает общий тумблер перевода так же, как колонка
  расшифровки.

## 6. Критерии приёмки

1. `GET /api/reels` без параметров возвращает то же, что и до правки, плюс новое поле — сверка
   с эталоном `.baseline/` скриптом `scripts/verify_sources.py`.
2. Поиск `q` по прежним запросам находит не меньше, чем находил (проверить на нескольких словах).
3. `--dry-run` бэкфилла печатает число подходящих подписей и не делает ни одного перевода.
4. Повторный запуск бэкфилла не переводит заново уже переведённое.
5. В карточке переключатель у текста поста работает и исчезает там, где перевода нет.
6. `pytest`, `ruff` по изменённым файлам, `npm run build` — зелёные.
